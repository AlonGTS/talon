KEY THINGS LEARNED ABOUT PX4 vs ARDUPLANE (for mavlink_client.py)
---------------------------------------------------------------------
- ArduPlane GUIDED: yaw sent RAW (rudder command), roll/pitch composed
  onto current attitude. Proven working.
- PX4 OFFBOARD: all three axes (roll/pitch/yaw) composed onto current
  attitude as an absolute setpoint. Implemented but NOT yet verified
  on the bench because mode never actually engages (see above) — once
  OFFBOARD is confirmed sticking, still need to verify this composition
  is correct in practice (thrust scaling, sign conventions, etc.)
- PX4 custom_mode encoding: main_mode packed into bits 16-23 of the
  32-bit custom_mode field (main_mode << 16). OFFBOARD = 6, MANUAL = 1.
  This encoding itself is confirmed correct (MANUAL switch during
  disarm() does visibly take effect).
- MAV_RESULT_ACCEPTED on DO_SET_MODE ONLY means PX4 parsed the message.
  It does NOT mean the mode transition was actually applied — PX4
  validates that separately and can silently stay in the old mode.
  Ground truth must come from HEARTBEAT.custom_mode / base_mode, not
  the COMMAND_ACK.

GROUND-TRUTH DIAGNOSIS (via live /tmp/talon.log, same method as
Session 1 — HEARTBEAT, not ACKs)
------------------------------------------------------------------
1. SET_ATTITUDE_TARGET *was* being sent correctly and continuously —
   confirmed in the log (composed roll/pitch/yaw, correct thrust,
   fresh attitude age each frame). Not a sending bug.
2. DO_SET_MODE(OFFBOARD) got MAV_RESULT_ACCEPTED (x2) as usual, but
   HEARTBEAT stayed at mode=MANUAL after arming. Same "ACK != applied"
   trap as Session 1, one level further now that arming works.
   -> Since PX4 was never actually in OFFBOARD, it correctly ignored
      all our SET_ATTITUDE_TARGET messages. That's the whole symptom.
3. Hypothesis A: COM_RCL_EXCEPT (bitmask) was 0 on the FC. No RC
   transmitter is ever connected on this rig, so PX4 treats "RC lost"
   as true from boot, and by default that blocks/reverts OFFBOARD
   entry unless Offboard's bit (bit 2, value 4) is in the exception
   mask. Implemented as an automatic fixup (see CODE CHANGES) —
   necessary but turned out NOT sufficient by itself (see next).
4. Ran the live test again with the RC-exception fix applied. Mode
   *still* never showed OFFBOARD. Worse: ~9 seconds after arming, PX4
   forced the mode to LAND on its own (MAVProxy printed "LAND> Mode
   LAND" — that's PX4 commanding this, not our code), then the
   land-detector oscillated "Takeoff detected" / "Landing detected"
   repeatedly for the rest of the run, and the FC eventually
   auto-disarmed itself with no input from us.
5. Hypothesis B (current leading theory): mav.parm has EKF2_GPS_CTRL=7
   — the EKF is still configured to require/use GPS for its position
   estimate, but there is no GPS receiver on this airframe at all, so
   position never validates. This trips PX4's *generic* position-
   invalid failsafe (separate from the offboard-entry precondition),
   which force-switches to LAND regardless of flight mode. Per PX4
   docs/GitHub issues, pure attitude+thrust offboard setpoints should
   NOT themselves require a position estimate — this failsafe is a
   different, broader safety check that fires whenever position is
   invalid while armed, independent of what setpoints are being sent.
   COM_ARM_WO_GPS=2 only relaxes *arming* pre-checks; it does not stop
   this runtime failsafe.

CODE CHANGES MADE THIS SESSION (in mavlink_client.py, NOT YET COMMITTED)
--------------------------------------------------------------------------
Added `_apply_px4_fixed_params()`, called from connect() whenever
autopilot == "px4", right after wait_heartbeat() and before _enabled
is set True. Blind-writes (PARAM_SET, no read-modify-write) three FC
params every time the app connects:
    COM_RCL_EXCEPT  = 4           (bit 2: exempt Offboard from RC-loss failsafe)
    EKF2_GPS_CTRL   = 0           (stop the EKF waiting on GPS — none installed)
    EKF2_NOAID_TOUT = 2000000000  (µs, ~33 min — extend dead-reckoning grace
                                    period so position doesn't re-flag invalid
                                    mid-flight)
These live in the _PX4_FIXED_PARAMS dict near the top-ish of the PX4
section of mavlink_client.py. Values are blind (not read-modify-write)
deliberately — see next paragraph for why.

ENGINEERING DETOUR (fixed, but worth knowing about)
-----------------------------------------------------
First attempt used read-modify-write (PARAM_REQUEST_READ) so as not to
clobber any other bits/values already set. This reliably timed out:
  a) Initial bug: the fixups ran AFTER _enabled was set True, so the
     background _telemetry_reader thread immediately started
     recv_match()-ing concurrently on the same connection. pymavlink's
     recv_match discards any message not matching its own type filter
     while scanning for one that does — so it was silently eating our
     PARAM_VALUE replies before our read loop ever saw them. Fixed by
     reordering (fixups now run before _enabled = True).
  b) Even after that fix, reads still timed out (tried up to a 20s
     budget per param). Cause: MAVProxy does its own full ~1150-param
     bulk fetch immediately after connecting (visible as "Received N
     parameters / Saved N+1 parameters to mav.parm" in MAVProxy's own
     output when it happens), which floods/delays PARAM_VALUE traffic
     on the same link for a while.
  Resolution: gave up on reading current values first. This rig has a
  single fixed role (no RC, no GPS, attitude-only offboard), so there
  was nothing worth preserving — switched to blind param_set_send for
  all three params. Added 'PARAM_VALUE' to _telemetry_reader's watched
  message types so a confirmation prints asynchronously (`[FC]
  PARAM_VALUE <name> = <value>`) if/when PX4 echoes one back, without
  blocking connect() on it.

BUG FOUND #1 (real, fixed): target_system/target_component were never
being set
-----------------------------------------------------------------------
mavlink_client.connect() only ever called `_connection.wait_heartbeat()`
and then immediately used `_connection.target_system` /
`.target_component`. Turns out that's a classic pymavlink footgun:
  - wait_heartbeat() does NOT set target_system/target_component itself.
  - target_system is a property that returns pymavlink's own internal
    self.sysid, which DOES auto-populate, but only as a side effect of
    processing a HEARTBEAT that looks vehicle-like (pymavlink's
    probably_vehicle_heartbeat() filter), and only from the FIRST such
    HEARTBEAT ever seen on the connection. If the very first HEARTBEAT
    wait_heartbeat() happens to catch is MAVProxy's own proxy heartbeat
    (not the FC's), it still returns successfully (type filter matched)
    but target_system stays 0.
  - target_component is a property backed by param_sysid[1], which is
    NEVER auto-populated from a heartbeat at all — it just stays 0
    unless you explicitly assign `.target_component = ...` yourself.
  Confirmed directly: a one-shot connect showed target_system=0,
  target_component=0 despite "heartbeat received" printing fine.
  This means our PARAM_SET/PARAM_REQUEST_READ messages (and possibly
  other things) have likely been addressed to component 0 this whole
  session. ARM / DO_SET_MODE / reboot commands still worked because
  PX4's COMMAND_LONG handling is apparently broadcast-tolerant of
  compid 0 — but PARAM_SET may not get the same tolerance, which would
  explain "it didn't work" independent of any EKF2/reboot timing theory.

  FIX (in mavlink_client.py, uncommitted): added `_lock_onto_autopilot()`,
  which loops recv_match(type='HEARTBEAT') until it sees one specifically
  from srcComponent == MAV_COMP_ID_AUTOPILOT1 (1), then explicitly sets
  target_system/target_component from that message. connect() now calls
  this instead of the bare wait_heartbeat(), with a 15s budget, and
  raises (triggering the existing fallback path) if it never sees one.
